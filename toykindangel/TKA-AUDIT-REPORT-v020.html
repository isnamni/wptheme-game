این گزارش، وضعیت قالب toykindangel را پس از اعمال اصلاحات کنترل‌شدهٔ مرحلهٔ دوم نشان می‌دهد. اصلاحات فقط روی مواردی متمرکز بوده‌اند که در گزارش قبلی (v0.19.0) به‌عنوان مشکل واقعی یا ریسک معماری شناسایی شده بودند و با بررسی کد تأیید شده‌اند. هیچ تغییر سلیقه‌ای، refactor کامل، یا تغییر رفتار ظاهری انجام نشده است.

هیچ فایلی خارج از محدودهٔ مشکلات شناسایی‌شده تغییر نکرده است. ساختار UI، HTML، CSS، JS، URLها، WooCommerce hooks، و قراردادهای داخلی (TKA_WP، cache functions، AJAX/REST endpoints) دست‌نخورده باقی مانده‌اند.

نتیجهٔ کلی: تمام مشکلات Production Risk (Priority 1) که در گزارش قبلی شناسایی شده بودند، اصلاح و تأیید شده‌اند. قالب اکنون از نظر N+1 روی صفحات پر‌بازدید (Homepage، Shop، Category، Categories، Footer)، صحت Admin Dashboard، و SEO schema در وضعیت مناسب‌تری برای مقیاس ۳٬۰۰۰ محصول + ۴٬۰۰۰ بازدید روزانه است.

H1 — Admin: wc_get_orders(limit=-1) FIXED

محل:
inc/admin-meta.php:297-365 (toykindangel_order_total_sum)
مشکل چه بود؟
تابع تمام order IDهای ماه را با wc_get_orders('limit'=>-1, 'return'=>'ids') در PHP memory می‌ریخت، سپس implode(',', $ids) می‌کرد و در یک SQL IN(...) قرار می‌داد. در فروشگاه پُر‌تراکنش (۳٬۰۰۰ محصول + ۴٬۰۰۰ بازدید)، ماهانه می‌توانست ده‌ها هزار سفارش باشد → آرایهٔ PHP بزرگ + SQL string بزرگ + فشار به max_allowed_packet و query planner.
چه تغییری انجام شد؟
بازنویسی به یک aggregate SUM مستقیم با WHERE status IN (...) AND date >= %s:
  • HPOS path: SELECT SUM(total_amount) FROM wc_orders WHERE status IN (...) AND date_created_gmt >= %s
  • CPT fallback: SELECT SUM(pm.meta_value+0) FROM postmeta pm INNER JOIN posts p ... WHERE pm.meta_key='_order_total' AND p.post_type='shop_order' AND p.post_status IN (...) AND p.post_date_gmt >= %s
  • هیچ IDای در PHP memory ریخته نمی‌شود. هیچ IN(...) عظیمی ساخته نمی‌شود.
  • Status‌ها با esc_sql ایمن شده‌اند؛ date با $wpdb->prepare.
چرا SQL مستقیم؟
API استاندارد WC (wc_get_orders) برای گرفتن objects یا IDs طراحی شده، نه برای aggregate. برای SUM، SQL مستقیم روی جدول active order storage روش پیشنهادی خود WooCommerce است. این الگو قبلاً در کد موجود بود (فقط با ID materialization)، پس ادامهٔ همان رویکرد است نه تغییر معماری.
اثر مورد انتظار:
حذف PHP memory growth + حذف IN clause بزرگ. سرعت dashboard widget در فروشگاه پُر‌تراکنش به‌طور قابل‌توجه بهبود می‌یابد.
وضعیت نهایی:
FIXED

۶. نتیجهٔ تست‌ها

بررسی syntax

php -l در محیط sandbox موجود نبود (PHP CLI نصب نبود). به‌جای آن:

  • بررسی‌گر پرانتز/براکت روی همهٔ ۹ فایل تغییرکرده اجرا شد (با stripper بهبودیافته برای string‌ها).
  • بررسی دستی function definitions و closing braces — همه متوازن.
  • بررسی <?php در شروع همهٔ فایل‌ها — همهٔ فایل‌ها با <?php شروع می‌شوند.
  • بررسی grep برای خطاهای واضح (string‌های unclosed، پرانتز‌های نامتوازن) — یافت نشد.

بررسی diff

  • همهٔ ۹ فایل فقط تغییرات لازم را دارند (هیچ whitespace mass-change ای نیست).
  • markup HTML ۱:۱ حفظ شده (برای C1، C2، C3، C4، H3).
  • هیچ فایلی خارج از محدودهٔ مشکلات شناسایی‌شده تغییر نکرده.
  • هیچ قرارداد داخلی (TKA_WP، cache functions، AJAX/REST endpoints، WC hooks) تغییر نکرده.

تست‌های نیازمند محیط واقعی WP

موارد زیر را نمی‌توان بدون محیط WordPress + WooCommerce با دادهٔ واقعی تأیید کرد:

  • runtime query count قبل/بعد (نیاز به Query Monitor یا SAVEQUERIES)
  • HTML output PDP برای تأیید حذف duplicate schema (H4)
  • رفتار HPOS در admin dashboard (L7)
  • رفتار cache invalidation بعد از ویرایش term
