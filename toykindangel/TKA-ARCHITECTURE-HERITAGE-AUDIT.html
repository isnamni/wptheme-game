این قالب از یک دموی HTML/JS شروع شده و بعد به WordPress متصل شده. این الگو در خودش اشکالی ندارد — ولی باعث شده چندین «لایهٔ پل» بین دمو و WordPress بسازید که اگر از صفر WordPress-first طراحی می‌کردید، وجود نداشتند. مهم‌ترین آن‌ها:

  1. window.TKA_WP — یک لایهٔ واسط بین PHP و JS که داده‌های WooCommerce را به JS demo می‌دهد. در storefront واقعی، ۶ از ۸ کلید آن تکراری با SSR است.
  2. data.js — دیتاست دمو (محصولات، دسته‌ها، برندها) که بعد از import دمو دیگر نیاز نیست ولی هنوز در homepage و /categories/ load می‌شود.
  3. app.js — رندرر JS که با SSR guard کار می‌کند. در storefront واقعی، بخش rails آن dead code است.
  4. مرور درختی /categories/ — کاملاً JS-rendered است (SEO-blind). این تنها مورد بحرانی است.
  5. دو نسخه از demo dataset — data.js (JS) و inc/demo/data.php (PHP) همین داده را دارند.
خبر خوب: هیچ‌کدام از این موارد باگ نیستند. قالب کار می‌کند، SSR فعال است، و app.js با guard کار می‌کند. ولی در یک قالب WordPress-first حرفه‌ای، این لایه‌ها حذف یا ساده می‌شدند.

۲. پیش‌فرض شما — و پاسخ کوتاه

سؤال شما:

«اگر از صفر قالب را برای WordPress/WooCommerce می‌نوشتیم و دیتای دمو را هم در تنظیمات تعریف می‌کردیم (کاربر بعد از نصب import می‌کند)، آیا هنوز به ساختار TKA_WP نیاز داشتیم؟»

پاسخ کوتاه:

نه — به این شکل از TKA_WP نیاز نداشتید.

دلیل:

  • در معماری فعلی، TKA_WP یک پل بین دموی JS و WordPress است. وقتی دمو فعال است، JS از window.TKA (دیتاست دمو) render می‌کند. TKA_WP داده‌های واقعی WordPress را روی TKA overlay می‌کند تا JS همان UI را با داده واقعی نشان دهد.
  • اگر WordPress-first می‌بودید، PHP مستقیماً HTML را از WooCommerce می‌ساخت (که اکنون inc/front-ssr.php همین کار را می‌کند) و JS فقط برای تعاملات (کلیک، AJAX، اسلایدر) استفاده می‌شد. در آن صورت، فقط چند متغیر کوچک (AJAX URL، nonce، product ID) نیاز بود — نه کل payload.
ولی نکتهٔ مهم: حذف کامل TKA_WP الان ریسک بالایی دارد چون app.js و main.js به آن وابسته‌اند. این یک refactor معماری است نه یک fix. این گزارش فقط شناسایی می‌کند، نه توصیهٔ حذف فوری.

داده از کجا می‌آید:

چرا این الگو انتخاب شده:
چون در دموی HTML اصلی، درخت توسط JS paint می‌شده (با data.js). وقتی به WordPress تبدیل شد، به‌جای rewrite کردن به SSR، داده از data.js به TKA_WP تغییر کرد ولی render همچنان با JS ماند.
در یک قالب WordPress-first:
این بخش حتماً SSR می‌شد. داده در toykindangel_cats_data() موجود است — فقط کافی است PHP آن را به HTML تبدیل کند. JS فقط برای کلیک/accordion/search می‌ماند.
ریسک fix:
متوسط. باید PHP renderer نوشته شود که همان markup app.js را تولید کند (crail, cpanel, cgroup, ctile). بعد app.js فقط به event handlers (click, accordion, search) کاهش می‌یابد. ~۱۰۰-۱۵۰ خط PHP + ساده‌سازی app.js.
منفعت:
  • SEO: crawlerها کل درخت دسته را می‌بینند (internal linking بهتر)
  • TKA_WP.categories در /categories/ حذف می‌شود (~۵-۱۰KB)
  • صفحه بدون JS هم کار می‌کند (progressive enhancement واقعی)

۱۰. اگر از صفر WordPress-first می‌ساختیم

این سناریوی فرضی شماست:

سناریوی WordPress-first:

  1. قالب را برای WordPress/WooCommerce از صفر می‌نوشتید.
  2. دیتای دمو را در تنظیمات/داده‌های وردپرس تعریف می‌کردید (نه در یک فایل JS).

۱۳. نتیجه‌گیری

پاسخ به سؤال اصلی شما:

بله، قالب شما میراث قابل‌توجهی از تبدیل HTML→WordPress دارد. مهم‌ترین آن‌ها:

  1. TKA_WP یک پل بین demo JS و WordPress است که در storefront واقعی، ۶ از ۸ کلیدش تکراری با SSR است.
  2. data.js بعد از import دمو دیگر نیاز ندارد ولی هنوز load می‌شود.
  3. app.js rails renderers در storefront واقعی dead code هستند (SSR guard).
  4. مرور درختی /categories/ کاملاً JS-rendered است (SEO-blind) — تنها مورد بحرانی.

آیا این یک «اشتباه تبدیل» است؟

نه کاملاً. این الگو (demo-first → WordPress overlay) در قالب‌های تجاری رایج است و کار می‌کند. ولی اگر هدف شما یک قالب WordPress-first حرفه‌ای است، این لایه‌ها ساده می‌شدند.

آیا باید الان تغییر کند؟

برای Production فعلی: نه. قالب کار می‌کند، SEO برای homepage/shop/PDP درست است (همه SSR هستند)، و fallback mode کار می‌کند. ولی:

  • Q1+Q2+Q3 (کم‌ریسک) را می‌توانید الان انجام دهید — ~۲۰KB کمتر در هر homepage.
  • R1 (SSR /categories/ tree) را قبل از Production انجام دهید — SEO واقعی.
  • R2 (حذف کامل) را به نسخهٔ بعد موکول کنید.

نکتهٔ نهایی:

این گزارش هیچ کدی را تغییر نداد. فقط نقشهٔ معماری و «میراث» را شناسایی کرد. تصمیم refactor با شماست — بر اساس منفعت vs ریسک و زمان موجود.

نقاط قوت قالب (برای انصاف):
  • SSR برای homepage rails، shop، category، PDP — همه درست
  • لایهٔ cache با event invalidation — طراحی درست
  • WooCommerce hooks استاندارد
  • AJAX/REST endpoints با throttle و cache
  • Demo importer idempotent با separate settings variant
  • صفر cron، صفر HTTP خروجی
این‌ها نشان می‌دهد بخش‌های اصلی قالب WordPress-first طراحی شده‌اند. میراث تبدیل فقط در «لایهٔ پل demo→WP» (TKA_WP + data.js + app.js renderers) متمرکز است.
